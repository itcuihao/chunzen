## Project Overview

**春蝉 (ChunZen)** — A VSCode extension for immersive academic paper reading. Opens PDFs in a custom editor with real-time sentence-level translation (hover triggers translation) and journal metadata lookup (IF, CAS ranking, JCR quartile).

## Build & Run

```bash
npm run compile          # webpack multi-target build → dist/{extension,panel,pdfViewer}.js
npm run watch            # webpack --watch
npm run package          # production build (for vsce package)
npm run typecheck        # tsc --noEmit (src only)
npm test                 # unit tests + PDF page layout snapshots (no vscode needed)
UPDATE_SNAPSHOTS=1 npm test   # regenerate tests/__snapshots__/*.json after an intentional layout change — review the diff before committing
npm run deploy           # scripts/build.sh local — generate src/build-info.ts, build, package, install
npm run release          # scripts/release.js — bump versions & tag
```

Press F5 in VSCode to launch the Extension Development Host.
`npm run lint` uses `.eslintrc.json` (eslint:recommended + @typescript-eslint/recommended) and is currently clean (0 errors, 0 warnings) — keep it that way.
`out/` and `dist/` are build outputs and are gitignored; `src/build-info.ts` is generated by `scripts/build.sh`.

### Data Flow

1. User opens a `.pdf` → `PdfEditorProvider` renders PDF.js webview
2. `textLayer.ts` extracts text, groups lines/columns into paragraphs, splits into sentences (optionally uses an external layout model via `chunzen.layout.*`, falling back to rules)
3. Hover (debounced) sends `sentence-hover` → `TranslationService.translate()` → result posted to side panel
4. Page-level translation (`translate-page`), AI explain, MinerU parse, figure screenshot, highlights and export are driven from the side panel through `SidePanelProvider`
5. DOI/ISSN/journal from first-page text → `DoiResolver` / `JournalService` → Journal tab

### Webpack Multi-Target Build

`webpack.config.js` has three configs: **extension** (node, commonjs2, `vscode` external), **panel** (web, React + CSS via postcss/tailwind), **pdfViewer** (web). Providers reference built artifacts in `dist/`. The vsix is packaged with `--no-dependencies`, so everything must be bundled by webpack.

### Translation Engines

- Engines implement `TranslationEngine` (`types/models.ts`); LLM-style engines (only OpenAI-compatible; Anthropic's format is intentionally unsupported) also implement `complete(system, user)`, which `TranslationService.completeWithLlm` uses for AI explain. `usesGlossaryPrompt: true` means the engine applies the glossary via prompt; otherwise `TranslationService` post-processes with `applyGlossary`.
- `engines/registry.ts` owns the engine list. Priority = user's `chunzen.translation.priority`, normalized (unknown/duplicate dropped, newly added engines appended), so adding an engine never requires users to edit settings.
- **Adding an engine**: implement the class → add to `ENGINES` in `registry.ts` → add `chunzen.translation.<name>.*` to `package.json` → add the field set to `ConfigService.getTranslationConfig/getEngineConfigs` and `engineFields` in `SettingsTab.tsx`. `getEngineStatuses()` and fallback need no change.
- Engine config accepts a `configOverride` (used by "test connection" with unsaved inputs).

### Configuration

- Declared in `package.json` `contributes.configuration`. Read through `ConfigService` only; do not scatter `getConfiguration(...).get(key, <literal default>)` with new literals.
- Defaults live in exactly one code place: `engines/defaults.ts` (OpenAI), `settingsNormalize.ts` (numeric ranges, layout endpoint). Numeric/enum constraints are also declared in `package.json` (`minimum`/`maximum`/`enum`) — keep both in sync.
- Do not add user-facing settings for features that are disabled. MinerU is disabled (`getMineruConfig()` returns `enable: false`, no `chunzen.mineru.*` settings, UI entry commented out); re-enabling means restoring settings + UI together.
- Only OpenAI-compatible chat-completions format is supported for LLM engines (intentional).
- Changing a default that existing users may rely on needs a migration, not just a new literal. Example: the OpenAI-compatible default moved from OpenAI to DeepSeek, so `ConfigService.pinLegacyOpenAiDefaults()` (run at activation) writes the old values back for users who already set an API key but never set baseUrl/model. Keep the decision logic pure (`legacyOpenAiPins`) so it stays testable.

### Communication Protocol

All message types in `src/types/messages.ts` (`PdfViewerToExtMessage`, `ExtToPanelMessage`, `PanelToExtMessage`). Panel sends `request-state` on mount; extension responds with `init-state`. When adding a message, update the union type and handle it in `SidePanelProvider` / `PdfEditorProvider`.

## Key Technical Details

- **PDF.js 3.11.174 is loaded from cdnjs** (CSP allows `cdnjs.cloudflare.com`), not bundled. `pdfjs-dist` is pinned to the same `3.11.174` in devDependencies and used **only** by `tests/support/pageHarness.ts`; keep both versions in sync when upgrading (layout differs between PDF.js majors, e.g. 5.x finds no horizontal rules).
- **CSP nonce** per webview HTML via `utils/nonce.ts`; `retainContextWhenHidden: true`; `supportsMultipleEditorsPerDocument: false`
- Network calls go through `utils/fetch.ts` `customFetch` (proxy aware) — use it for new HTTP code
- **Tests**: only modules without a `vscode` import are tested, via `node --test` with Node's native TypeScript stripping (Node ≥ 22.6) plus `tests/support/resolve-ts.mjs` for extensionless imports. Use `import type` for type-only imports in modules the tests load. Keep new logic in pure modules to keep it testable.
- **Page layout snapshots** (`tests/pageLayout.test.ts`): run the real `getPageText` + `buildTextLayer` on pages of the PDFs in `pdf/` and compare a fingerprint (block type, column, rounded box, sentence count, text hash — no prose) with the committed snapshot. They skip if the sample PDFs are absent. A failing snapshot means layout output changed: decide whether that is intended, then regenerate.
- **tsconfig**: `jsx: "react-jsx"`, `jsxImportSource: "react"`, `include: ["src"]`

## Known Debt

- `webviews/pdfViewer/textLayer.ts` (~2770 lines): `buildTextLayer` is a ~850-line function whose phases share many local variables. It is now covered by page-level snapshots (2 papers, 11 pages), so extract pure helpers out of it incrementally and let the snapshots catch regressions. Snapshots only cover these two papers' layouts (no tables-with-rules, sidebars or 3-column pages).
- `webviews/sidePanel/components/TranslationTab.tsx` (~1410 lines) is the component only (state, effects, layout). Its internal `render*` closures share component state; splitting them means passing props explicitly — do that only with the extension running to verify.
- `webviews/sidePanel/components/TextRenderers.tsx` (~775 lines) holds the large citation/figure/DOI render functions verbatim; they are hook-free but have no tests (they return React nodes).
- `GlossaryService` and `journalService` sources are not registry-driven like engines.
- No webview/integration tests beyond the layout snapshots.
